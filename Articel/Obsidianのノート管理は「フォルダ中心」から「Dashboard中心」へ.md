# Obsidianのノート管理は「フォルダ中心」から「Dashboard中心」へ

## はじめに

Obsidianを使い続けていると、ノートの数は確実に増えていく。

デイリーノート、読書メモ、Web記事のClippings、仕事の記録、行きたい店、記事のアイデア。最初はフォルダを分けるだけで十分だったが、ノートが増えるほど「どこに保存したか」よりも「今見るべきノートはどれか」が分からなくなってきた。

フォルダを開けばノートは見つかる。しかし、そこに並んでいるのはファイル名の一覧だ。

- まだ処理していないノートはどれか
- 今進めているものは何か
- 記事にできそうな情報はどれか
- しばらく更新していないノートは何か
- 最近追加した情報のうち、次に見るべきものはどれか

こうした問いに、フォルダだけで答えるのは難しい。

そこで、ノートが増えてきた段階では、分野ごとにObsidianのBasesを用意し、Dashboardを入口にして管理する方式がよいのではないかと考えている。

## フォルダ管理が悪いわけではない

最初に整理しておきたいのは、Dashboard方式に移行するからといって、フォルダが不要になるわけではないということだ。

フォルダには、今でも明確な役割がある。

- 情報の保存場所を大まかに分ける
- 読書、仕事、生活記録など、情報の由来を示す
- 自動化ツールの出力先を固定する
- 公開用と非公開用のノートを分離する
- バックアップや権限管理の境界にする

一方、フォルダは基本的に「一つの場所」しか表現できない。

例えば、あるClippingが「AI」に関する情報であり、「記事化候補」であり、「未処理」であり、「今週追加されたもの」でもある場合、フォルダだけでこれらを同時に表すのは難しい。分類軸ごとにフォルダを増やすと、どこへ置くべきか迷うようになる。

フォルダは保管場所として優秀だが、状態を見ながら仕事を進める操作画面としては弱い。

## ノートが増えると、管理したいものが変わる

ノートが少ないうちは、「どこに何があるか」を把握できれば十分だ。

しかし、ノートが増えると、知りたいことが変わってくる。

「どこにあるか」ではなく、次のようなことを知りたくなる。

- 未処理か、処理済みか
- 進行中か、完了済みか
- 優先度は高いか
- 次に何へ使うのか
- 最後に更新したのはいつか
- どのテーマと関係しているか

これはファイル管理というより、状態管理に近い。

フォルダ中心の管理からDashboard中心の管理へ移る意味は、見た目をきれいにすることではない。ノートを「保存されたファイル」ではなく、「次の処理を待つ情報」として扱えるようにすることだと思う。

## Dashboard方式の基本構造

Dashboard方式は、次の4層に分けると考えやすい。

```mermaid
flowchart LR
    A["フォルダ<br>保管場所・大分類"] --> B["プロパティ<br>種類・状態・用途"]
    B --> C["Bases<br>検索・抽出・集計"]
    C --> D["Dashboard<br>次に見る・やる入口"]
```

### 1. フォルダは保管場所

読書メモは読書フォルダ、ClippingsはClippingsフォルダ、記事は記事フォルダというように、大きな責任範囲だけを分ける。

細かな状態までフォルダで表現しようとしないことが重要だ。

### 2. プロパティは状態と意味

ノートに最低限のプロパティを持たせる。

```yaml
type: clipping
status: unprocessed
created: 2026-08-08
updated: 2026-08-08
genre: knowledge-management
next_use: article
```

ここで大切なのは、最初から項目を増やしすぎないことだと思う。

`type`、`status`、`created`、`updated`、`genre`または`area`、`next_use`くらいから始めればよい。入力されないプロパティを大量に用意しても、管理項目だけが増えて運用が続かない。

### 3. Basesは検索・抽出・集計

Basesでは、フォルダやプロパティを条件にして、同じノート群から複数のビューを作る。

例えばClippingsなら、次のようなビューが考えられる。

- 要約待ち
- 記事化候補
- 行動に反映するもの
- 追加調査するもの
- 保管のみ
- 最近追加したもの

ノートを別の場所へ移動しなくても、条件を変えるだけで複数の切り口から見られるのがよい。

### 4. Dashboardは人が見る入口

Baseファイルを直接開くだけでも一覧は見られるが、Markdownノートに必要なビューを埋め込むと、何のための一覧なのかを説明できる。

```md
## 今処理するもの
![[Clippings.base#要約待ち]]

## 次の記事に使えそうなもの
![[Clippings.base#記事化候補]]

## 最近追加したもの
![[Clippings.base#最近追加]]
```

Dashboardには一覧だけでなく、「この画面をいつ見るか」「上から何を処理するか」も書いておける。

Baseがデータの抽出を担当し、Dashboardが人間の判断を助ける。この二つを分けるのが使いやすそうだ。

## 分野ごとにどんなDashboardを作るか

自分のVaultなら、まず次の単位でDashboardを作るのがよさそうだと考えている。

### Clippings Dashboard

外部から保存した記事や動画を、保存したまま沈ませないための画面。

- 要約待ち
- 自分との関係を未整理
- 記事化候補
- 行動候補
- 調査候補
- 保管のみ

Clippingsで重要なのは、ジャンル別にきれいに並べることより、「次に何へ変換するか」を見えるようにすることだと思う。

### Book Dashboard

読書ノートを、未読・読書中・読了だけでなく、読後の処理まで含めて管理する。

- 未読
- 読書中
- 読了済み
- レビュー待ち
- おすすめ
- 記事化できそうな本

実際に読書ノートでDashboardを作ってみると、1冊ずつのノートを探すよりも、「今読んでいる本」「感想を書いていない本」が一目で分かる方が便利だった。

### Ideas / Output Dashboard

アイデアを思いついたまま放置せず、公開までの流れとして見る。

- アイデア
- 調査中
- 構成作成中
- 下書き
- 公開準備
- 公開済み

アイデアと記事を別々の一覧で見るだけでなく、一つの流れとしてつなげられれば、「アイデアは多いのに記事にならない」という詰まりも見えやすくなる。

### Lists Dashboard

飲食店、施設、欲しい物、ツールなどは、カードや表形式との相性がよい。

- 行きたい場所
- 訪問済み
- 評価の高い店
- 購入候補
- 購入済み
- カテゴリ別一覧

フォルダを一つずつ開くより、状態や評価で並べ替えられる方が、実際に選ぶ場面で役に立つ。

### Review Dashboard

デイリーノート、目標、Routine、振り返りをつなぐ画面。

- 最近の日次ノート
- 未完了タスク
- 継続中の目標
- 振り返り未記入
- 最近のProblemとTry

記録の一覧ではなく、次の行動を決めるための画面として設計したい。

## 最後にHome Dashboardで横断する

分野別Dashboardが増えてきたら、その上にHome Dashboardを置く。

ただし、Home Dashboardにすべてのノートを並べる必要はない。ここに出すのは、今の自分が判断すべきものだけでよい。

- Inboxの未処理ノート
- 要約していないClippings
- 進行中のアイデアや記事
- レビュー待ちの読書ノート
- 最近更新したノート
- 一定期間動いていない進行中ノート

Home DashboardはVault全体の目次ではなく、「今日どこから手をつけるか」を判断する画面にする。

## Dashboard方式のよいところ

### ノートを移動せず、複数の切り口で見られる

同じノートを「AI」「記事化候補」「未処理」「今週追加」のすべてに表示できる。フォルダを細分化しなくてよくなる。

### 未処理が見える

ノートが増えること自体より、処理されていないノートが見えないことの方が問題だ。Dashboardがあれば、空欄のプロパティや未処理状態をそのまま作業リストにできる。

### 分類より行動を中心にできる

「何についてのノートか」だけでなく、「次にどうするか」で情報を並べられる。

### ノートが増えても入口を固定できる

毎回フォルダ構成を思い出さなくても、まずDashboardを開けばよい。ノート数が増えるほど、この入口の価値は大きくなると思う。

## 気をつけたいこと

### Dashboardを作りすぎない

細かなテーマごとにBaseとDashboardを作ると、今度はDashboardを探すことになる。

「同じプロパティと処理フローを使うノートは、一つのBaseにまとめる」くらいがちょうどよい。

### プロパティ入力を目的にしない

管理項目を増やしすぎると、ノートを書くよりプロパティを埋める時間の方が長くなる。

一覧で使わない項目は作らず、実際に欲しいビューから逆算してプロパティを決めるべきだと思う。

### いきなりファイルを移動しない

Dashboard方式を始めるために、既存ノートを一斉に移動する必要はない。

まずは現在のフォルダ構成を維持したままBaseを重ねる。運用してみて、フォルダが本当に不要だと分かってから整理すればよい。

### 空欄を異常ではなく処理対象として扱う

すべてのノートのプロパティが最初から埋まっている必要はない。

むしろ「statusが空欄」「要約がない」「next_useが未設定」といった状態を、未処理ビューで拾えるようにする方が現実的だ。

## 小さく始めるなら

最初からVault全体をDashboard化する必要はない。

次の順番で十分だと思う。

1. ノート数が多く、困っている分野を一つ選ぶ
2. その分野で知りたい状態を3つ決める
3. 必要最低限のプロパティを追加する
4. Baseに3つのビューを作る
5. MarkdownのDashboardへビューを埋め込む
6. 週に一度開いて、実際に処理する

例えばClippingsなら、最初は「要処理」「記事化候補」「保管のみ」の3ビューだけでもよい。

大切なのは豪華なDashboardを完成させることではなく、Dashboardを開くと次の行動が決まる状態を作ることだ。

## まとめ

Obsidianのノートが増えてきたら、管理の中心をフォルダからDashboardへ少しずつ移してもよいのではないかと思う。

役割を整理すると、次のようになる。

- フォルダは保管場所
- プロパティは状態と分類
- Basesは検索・抽出・集計
- Dashboardは次に見るもの、やることの入口

フォルダを捨てる必要はない。フォルダだけに、分類・状態管理・作業管理のすべてを背負わせないようにする。

ノートが少ないうちは、きれいに保存できれば十分かもしれない。しかし、ノートが増えた後に必要なのは、保存場所の一覧ではなく、今の自分に必要な情報を取り出し、次の行動へつなげる画面だ。

Dashboard方式は、Obsidianを「ノートを保管する場所」から「情報を動かす作業場」へ変えるための、一つの方法になりそうだ。
