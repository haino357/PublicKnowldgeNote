# Dashboardを13枚作って分かった、本体は「一覧」ではなく「状態の遷移」だった

## はじめに

ObsidianでDashboardを作り始めたときは、1枚だけだった。読書管理のDashboardを作って、便利だったので次を作った。

気づいたら13枚になっていた。仕事タスク、Clippings、記事、読書、画像素材、企業調査、飲食店、施設、目標、アイデア、業務Wiki……。

普通に考えると、これは失敗の兆候だ。管理画面が増えれば、管理画面の管理が必要になる。実際そうなりかけた。

そこから運用を整理して分かったのは、**Dashboardで本当に決めるべきなのは「どう並べるか」ではなく「次にどこへ動かすか」だった**ということだ。

## 13枚あっても破綻しなかった理由は「確認頻度」で層を分けたこと

まず、枚数そのものは問題ではなかった。問題は「毎回どれを見ればいいか分からない」ことだった。

なので、Dashboardを役割ではなく**確認頻度**で分けた。

| 頻度 | Dashboard | 目的 |
|---|---|---|
| 毎日 | Home / 仕事タスク | 今日の判断と期限 |
| 週次 | Clippings / 記事 / 読書 / アイデア | 溜まったものを処理する |
| 月次 | 画像素材 / 業務Wiki / 企業調査 | 鮮度と棚卸し |
| 必要時 | 飲食店 / 施設 / ナイトスポット | 探すときだけ開く |

毎日開くのは2枚だけ。残りは開くタイミングが決まっているので、視界に入らない。

この仕分けをしてから、「13枚ある」という感覚がなくなった。人間が同時に持てる入口は、せいぜい2つでいい。

## 作ってみて分かった、Dashboardの本体は一覧ではなかった

ここからが本題で、いちばん効いた部分だ。

Dashboardを作るとき、最初は「どの列を出すか」「どう並べ替えるか」を一生懸命考えていた。期限順、優先度順、更新日順。見た目の話だ。

だが運用してみると、一覧を眺めて終わる日が多かった。見えているのに、動かない。

原因ははっきりしていて、**一覧を見たあと「で、これをどうするのか」が決まっていなかった**からだ。

そこで各Dashboardに、状態の遷移図を書いた。これだけ。

```text
Clippings:  inbox → reviewed → used
                      ├─────→ reference
                      └─────→ deleted

仕事タスク:  todo → in-progress → review → done
                       └──────→ blocked → in-progress
             ※どの状態からでも → dropped

記事:        idea → draft → ready → published

アイデア:    spark → framed → building → shipped
                └──────────────────→ dropped
```

すると、一覧の意味が変わった。

それまで一覧は「溜まっているものを見る場所」だったが、遷移図を決めた後は「**次の状態に動かす対象を選ぶ場所**」になった。

Clippingを1件開いたとき、やることは「ちゃんと整理する」ではない。`reviewed` か `reference` か `deleted` のどれかを選ぶ、それだけだ。選択肢が3つに絞られると、10秒で決まる。

## 「処理する」が曖昧だったから手が止まっていた

振り返ると、以前つまずいていたのはここだった。

未処理のクリップを開いて、「これを処理しよう」と思う。だが「処理する」の定義がない。きちんと要約すべきか、記事にすべきか、タグを整えるべきか。考えているうちに、閉じる。

遷移先を決めておくと、この迷いが消える。**やることは「完璧に整理する」ではなく「次の状態を1つ選ぶ」**になるからだ。

しかも、`deleted` や `dropped` を遷移先として正式に用意したのが大きかった。見送りも立派な処理だと明示されるので、判断を保留しなくなる。実ファイルは消さず論理削除にしているので、捨てる心理的コストもない。

副産物として、状態が語彙として固定されるので、Base側のフィルタが安定した。表記揺れで消える列がなくなった。

## 状態を持たせない方がいいものもある

ただし、全部に `status` を付けたわけではない。

読書のDashboardは、明示的なステータスを持たせず、**日付プロパティから状態を算出している**。

| 条件 | 算出される状態 |
|---|---|
| 開始日なし・読了日なし | 未読 |
| 開始日あり・読了日なし | 読書中 |
| 読了日あり | 読了済 |
| 読了済 + 評価または感想が空 | レビュー待ち |

読書は「読み始めた日」「読み終えた日」を書けば状態が確定するので、人間が別途ステータスを更新する必要がない。**更新を忘れる余地を作らない**ほうが安全だった。

逆に仕事タスクは、`blocked`（前提待ち）のように日付から推測できない状態があるので、明示的に持たせている。

判断基準はシンプルで、**すでに書いている情報から状態が決まるなら算出、決まらないなら明示**でいい。

## 時間の上限を先に決めた

もう1つやったのが、Dashboardを見る時間の上限を決めたことだ。

- **日次 5〜10分**：Home → 今日の日次ノート → 仕事タスクの期限・要対応・進行中 → 今日のTOP1を決める
- **週次 30〜60分**：Clippings 10件、読書のレビュー待ち1冊、記事の執筆中と公開待ち確認、アイデアの今週分を絞る
- **月次**：増えた数ではなく、未処理数・実際に使った数を見る

ポイントは「全部やる」を目標にしないこと。Clippingsは週10件と決めている。300件を一度に片付けようとすると、たいてい一度も始まらない。

## 注意点：Dashboardは問題を解決しない

正直に書いておくと、Dashboardを13枚整備した時点でも、Clippingsの未処理は296件あった。実際に記事や行動へ使ったものは0件だった。

つまり**Dashboardは処理してくれない**。見えるようにするだけだ。

それでも作る価値があったのは、見えるようになったことで「これは放置している」と認めざるを得なくなったからだと思う。フォルダに埋まっていた頃は、溜まっていること自体に気づかなかった。

だから期待値としてはこのくらいが妥当だと思っている。

- ✅ 何が詰まっているか分かる
- ✅ 次に何をするか迷わなくなる
- ❌ 勝手に片付く

## 補足：一覧に出てこないときの確認順

運用していると「書いたはずのノートが出てこない」が必ず起きる。原因はだいたい決まっているので、上から順に見ている。

1. 対象フォルダの中にあるか
2. 拡張子や `type` など全体フィルタを満たしているか
3. `status` の値が定義済みの語彙と完全一致しているか（大文字小文字・表記揺れ）
4. 日付が `YYYY-MM-DD` として解釈できる形か
5. リスト型と文字列型のプロパティを混ぜていないか
6. 埋め込み側のビュー名と定義側のビュー名が一致しているか
7. 地図表示なら座標プロパティがあるか（住所やリンクだけでは出ない）

体感では3番と4番が大半を占める。状態の語彙を決めておくと、ここが減る。

## おわりに

Dashboardを作るとき、つい「どう見せるか」に時間をかけたくなる。列を整え、並べ替えを工夫し、ビューを増やす。

でも効いたのは、**そのノートが次にどの状態へ行けるのかを決めたこと**だった。逆に言えば、遷移図が書けないDashboardは、まだ操作画面になっていない一覧表なのだと思う。

もしこれから作るなら、順番はこうすすめたい。

1. 対象を1領域に絞る（読書でも、タスクでも）
2. **先に状態と遷移図を決める**（3〜4状態、見送り先も用意する）
3. その状態で絞り込むビューを作る
4. 確認頻度と時間上限を決める

ビューを増やすのは、そのあとで間に合う。
