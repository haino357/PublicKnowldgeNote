# Flutterアプリ開発の技術選定ガイド

新しくFlutterアプリを開発するときに、採用する技術と、その選定理由を確認するためのノート。主な対象はiOS／Androidアプリで、Web・デスクトップは追加要件として扱う。

> [!info] 調査時点と読み方
> 最終調査日：**2026-10-11**。対象はFlutter **3.47系**／Dart **3.13系**。最新パッチ番号や全パッケージの組み合わせ動作を保証する資料ではない。導入時にSDK・依存パッケージ・対象OSの互換性を確認する。
> 「デファクトスタンダード」は単一の構成を意味しない。このノートでは、公式推奨、実務で検討する有力候補、このノートの推奨案を区別する。採用率の統計順位は確認していない。

対象系列の根拠：[Flutterリリース一覧](https://docs.flutter.dev/release/release-notes)、[Dart 3.13の発表](https://dart.dev/blog/announcing-dart-3-13)。

## 1. 新規開発の推奨構成

以下は、一般的なAPI連携アプリを想定した**本ノートの推奨案**。全項目を初日から導入するのではなく、用途があるものを選ぶ。

| 分野 | 初期案 | 追加・変更する条件 |
| --- | --- | --- |
| SDK | Flutter stable＋FVMによるバージョン固定 | SDK更新は移行内容と対象OSを確認して実施 |
| 設計 | 機能単位の配置＋UI／Dataの責務分離＋Repository | 複雑な業務ルールや再利用が増えたらDomain／UseCase層を追加 |
| 状態管理・DI | Riverpod 3系 | BLoC経験のあるチームならBLoC／Cubitも同等に検討 |
| 画面遷移 | go_router | ごく単純な画面遷移ならNavigatorで開始可能 |
| HTTP | http | 認証処理の共通化、キャンセル、進捗通知などが必要ならDio |
| モデル | 不変のDartモデル | JSON変換はjson_serializable、copyWithや等価比較の生成はFreezedを検討 |
| 保存 | 用途に応じて選択 | 設定値はshared_preferences、機密値はflutter_secure_storage、構造化データはDrift |
| 品質 | flutter_lints、静的解析、Unit／Widgetテスト | 主要経路に統合テスト、ネイティブUI操作が必要ならPatrol |
| CI/CD | 既存CIで解析・テスト・ビルドを自動実行 | 配布はfastlaneやCodemagicなどを運用に合わせて選択 |

根拠と代替案は次節に記載する。RiverpodとBLoCを同じ責務に重複導入したり、状態管理の仕組みに加えて別のDIライブラリを無条件に追加したりする構成は初期案に含めない。

## 2. 分野別の技術選定と根拠

### 設計：責務分離を基本に、層は必要に応じて増やす

Flutter公式はUI／Dataの分離、ViewとViewModel、Repository、不変モデル、一方向のデータフローを推奨している。Domain／UseCase層は複雑さに応じた条件付きの選択であり、すべての操作に必須ではない。[公式アーキテクチャ推奨](https://docs.flutter.dev/app-architecture/recommendations)

本ノートでは、認証・検索・設定などの機能を単位にファイルをまとめ、画面から通信やDB操作を分離する構成を推奨する。Repositoryを複数組み合わせる処理や、複数画面で共通化したい業務ルールが増えた時点でUseCaseを検討する。[公式設計ガイド](https://docs.flutter.dev/app-architecture/guide)

RiverpodのNotifierに画面状態と操作を持たせる場合、それをViewModel相当として扱える。名称を揃えるためだけに同じ処理のViewModelをもう一つ作る必要はない、というのが本ノートの設計判断。

### 状態管理：RiverpodとBLoC／Cubitを要件で選ぶ

| 候補 | 向いている条件 | 位置づけ・出典 |
| --- | --- | --- |
| Riverpod | 非同期データの取得・キャッシュ・依存関係をまとめたい | 有力候補。[公式パッケージ](https://pub.dev/packages/flutter_riverpod) |
| BLoC／Cubit | 状態遷移や実装形式をチームで揃えたい | 有力候補。CubitとBlocの両方をFlutterから利用可能。[公式パッケージ](https://pub.dev/packages/flutter_bloc) |
| ChangeNotifier＋provider | SDK中心の構成や既存資産を活かしたい | 公式はChangeNotifierを条件付きで推奨し、DIではproviderを紹介。[公式推奨](https://docs.flutter.dev/app-architecture/recommendations) |

用途別の適性は本ノートの判断。公開パッケージの人気指標だけで、市場全体の採用率や優劣を断定しない。

Riverpodの新規実装では、ユーザー操作で変更する状態に`Notifier`／`AsyncNotifier`、取得中心の処理に`FutureProvider`／`StreamProvider`などを使い分ける。`AsyncValue`で読み込み中・成功・失敗を扱う。[Providerの公式説明](https://riverpod.dev/docs/concepts2/providers)

`StateProvider`、`StateNotifierProvider`、`ChangeNotifierProvider`はRiverpod 3でlegacy側へ移動した。互換性のため残っているが、新規実装の第一候補にしない。この変更は**Riverpod内のAPI**についてであり、Flutter SDKのChangeNotifier全体が非推奨になったという意味ではない。[Riverpod 3の変更点](https://riverpod.dev/docs/whats_new)

### ルーティング：go_routerを第一候補にする

go_routerは公式推奨。Deep Link、URL、認証に応じたリダイレクトなどがあるアプリで検討する。単純なアプリはNavigatorでもよい。従来の`MaterialApp.routes`によるnamed routesは、大半のアプリでは推奨されていない。[公式ナビゲーションガイド](https://docs.flutter.dev/ui/navigation)、[go_router](https://pub.dev/packages/go_router)

### 通信・モデル：小さく始め、必要な機能を追加する

| 技術 | 採用する理由 | 本ノートの判断 |
| --- | --- | --- |
| http | Dart公式のHTTPクライアント。Clientを差し替えて構成できる | 単純なAPI連携の初期案。[http](https://pub.dev/packages/http) |
| Dio | Interceptor、キャンセル、ファイル送信、進捗通知などを提供 | 通信の共通処理が増えるアプリで検討。[Dio](https://pub.dev/packages/dio) |
| Freezed＋json_serializable | 不変モデルのcopyWith・等価比較とJSON変換の生成 | モデル数や定型処理の量に応じて導入。[Freezed](https://pub.dev/packages/freezed) |

Riverpodのコード生成は任意。公式は、Freezedなどですでにコード生成を使うプロジェクトでは採用しやすい一方、Riverpodのためだけに導入する価値は限定的と説明している。生成時間や開発時の手順も選定に含める。[コード生成の説明](https://riverpod.dev/docs/concepts/about_code_generation)

### 保存：データの性質で選ぶ

| 保存対象 | 候補 | 注意点・出典 |
| --- | --- | --- |
| テーマ、表示設定など | shared_preferences | 新規実装は`SharedPreferencesAsync`／`SharedPreferencesWithCache`を検討。重要データの永続化には不適切。[公式パッケージ](https://pub.dev/packages/shared_preferences) |
| 認証トークンなど | flutter_secure_storage | OS固有の安全な保存機構を利用。対応プラットフォームと設定を確認。[公式パッケージ](https://pub.dev/packages/flutter_secure_storage) |
| 関連するデータ、検索、履歴 | SQLite＋Drift | 型付きクエリ、トランザクション、マイグレーション、変更のStream購読が必要な場合に有力。[Drift](https://pub.dev/packages/drift) |

DBには単一の標準を置かず、検索・件数・同期・移行の要件から選ぶ。Driftを導入するだけでサーバーとのオフライン同期が完成するわけではない。同期を要する場合は競合解決や再送の設計を別途行う。

### UI・多言語・画面サイズ

Material 3／Cupertinoを起点に、対象OSや独自デザインに合わせて選択する。画面幅や入力手段に応じたレイアウトを設計し、スマートフォン用の画面をそのまま拡大するだけの構成を避ける。[公式レスポンシブ設計](https://docs.flutter.dev/ui/adaptive-responsive)

多言語対応ではFlutter公式のARB／`gen_l10n`を候補にする。UIライブラリの分離に伴うLocalizationの違いも確認する。[国際化ガイド](https://docs.flutter.dev/ui/internationalization)

### テスト・CI/CD・運用

Unitテストでロジック、Widgetテストで画面、統合テストで主要なユーザー操作を確認する。`integration_test`はFlutter SDKの仕組みだが、OSの権限ダイアログなどを直接操作できないため、その要件がある場合はPatrolを検討する。[公式テストガイド](https://docs.flutter.dev/testing/overview)

CI/CDの製品は一択ではない。公式はCodemagic・Bitriseなどと、GitHub Actionsなどの既存CIにfastlaneを組み合わせる方法を紹介している。[継続的デリバリー](https://docs.flutter.dev/deployment/cd)

本ノートでは、PR時にフォーマット・静的解析・テスト、配布前に対象OSのビルド・主要経路の実機確認を行う構成を推奨する。コード生成を使う場合は、生成物とソースの整合性もCIで確認する。クラッシュ監視は本番運用の要件として検討し、Firebaseを使う場合はCrashlyticsが候補になる。[Crashlytics公式](https://firebase.google.com/docs/crashlytics/flutter/get-started)

SDKはFVMなどでプロジェクト単位に固定する。[FVM](https://fvm.app/)

複数パッケージを管理する必要が生じた場合はDartのPub workspaces、横断スクリプトやバージョン管理にはMelosを検討する。小規模な単一アプリに最初から必須ではない。[Pub workspaces](https://dart.dev/tools/pub/workspaces)、[Melos](https://pub.dev/packages/melos)

## 3. 条件によって変更する部分

以下は本ノートの選定例。案件固有の情報は各プロジェクトで記録する。

| 条件 | 選定の調整 |
| --- | --- |
| 個人開発・小規模MVP | UI／Data分離を維持し、DB・UseCase・モノレポ・コード生成は必要になってから追加 |
| BLoCに習熟したチーム | Riverpodへの統一より、既存のBLoC／Cubitの運用とテスト資産を優先 |
| 複雑な業務ルール | Domain／UseCase層を検討し、UIと独立したテストを充実 |
| オフライン利用 | ローカルDB、同期方針、競合解決、再送、移行を一体で設計 |
| Web対応 | URL遷移、ブラウザー操作、Wasm互換性、初期ロードを検証 |
| デスクトップ対応 | ウィンドウサイズ、キーボード・マウス、プラグイン対応を検証 |
| バックエンド未確定 | Firebase／Supabase／既存APIをデータモデルと運用要件で比較 |

FirebaseにはFlutter向けのサービス統合があり、SupabaseにはPostgreSQLを利用する公式Flutterクライアントがある。Flutterの採用からバックエンドを自動的に決めない。[Firebase for Flutter](https://firebase.google.com/docs/flutter)、[Supabase Flutterガイド](https://supabase.com/docs/guides/getting-started/quickstarts/flutter)

## 4. 新しい変更・移行中・実験段階の技術

| 技術・変更 | 2026-10-11時点の確認内容 | 採用時の判断 |
| --- | --- | --- |
| Material／Cupertinoの独立パッケージ | Flutter 3.47で`material_ui`／`cupertino_ui`をオプトイン可能 | 依存パッケージが公開する型の互換性を確認して採用 |
| Dart Primary constructors | Dart 3.13で安定化 | クラス定義を簡潔にできる。等価比較・copyWith・JSON生成とは用途を区別 |
| Riverpod Mutations／Offline persistence | 実験段階 | 変更リスクを受け入れられる場合に限定して検証 |
| Flutter WebのWasm | `--wasm`で利用可能 | 依存パッケージとブラウザーを含めて確認 |
| Wasmの遅延ロード | mainチャネルの実験的機能として案内 | stable前提の初期構成には含めない |

Material／Cupertinoの独立パッケージには互換ブリッジがあるが、依存パッケージの公開APIに従来SDKの型が含まれる場合、型の不一致まで解消するものではない。[公式移行ガイド](https://docs.flutter.dev/release/breaking-changes/material-ui-and-cupertino-ui)

Primary constructorsはクラス宣言の簡潔化であり、データモデルの全機能を自動生成する仕組みではない。[Dart 3.13](https://dart.dev/blog/announcing-dart-3-13)

Riverpodの実験的APIはメジャーバージョン変更なしでも破壊的に変わる可能性がある。[Riverpod 3の変更点](https://riverpod.dev/docs/whats_new)

WebでWasmを使う場合、旧来の`dart:html`／`package:js`から`package:web`／`dart:js_interop`への移行が関係する。Wasm非対応時のJavaScriptフォールバックも含めて検証する。[公式Wasmガイド](https://docs.flutter.dev/platform-integration/web/wasm)

## 6. 次回更新時に確認する項目

このノートの保守用メモ。アプリ開発やVault全体に新しい運用ルールを課すものではない。

- Flutter stable更新時や、新しいアプリを始める前に、リリース一覧とBreaking changesを確認する。
- 各候補の公式ドキュメント、対応SDK・OS、メンテナンス状況を確認する。
- 実験段階から安定化した機能、非推奨になったAPI、移行が必要な依存を見直す。
- `last_verified`は実際に出典を再確認した日に更新する。文章の整形だけでは変更しない。
- 技術の推奨を変えた場合は、理由と出典を変更履歴に追記する。

ファイル名は維持し、本文とGit履歴で更新を追える形にする。案件ごとの採用決定・比較結果は案件の設計資料に残し、ここへ非公開情報を転記しない。
