# CI/CDをやさしく理解する

## まず一言でいうと

CI/CDは、コードを変更したあとに行う「確認」と「配布」を自動化する仕組みです。

たとえば、アプリに機能を追加したとき、人が毎回手作業でテストやビルドをする代わりに、決めておいた手順をコンピューターに実行させます。問題が見つかれば早く知らせ、問題がなければ配布できる状態にしたり、実際に利用者へ届けたりします。

## CI・継続的デリバリー・継続的デプロイ

| 用語 | 何をするか | 人の操作 |
|---|---|---|
| **CI**（継続的インテグレーション） | 変更を共有し、自動でビルド・テスト・解析する | 結果を確認する |
| **継続的デリバリー** | テストに通った変更を、いつでもリリースできる状態にする | 本番公開の直前に人が承認することが多い |
| **継続的デプロイ** | テストに通った変更を、本番環境へ自動で公開する | 通常の変更では承認操作を挟まない |

「CD」は継続的デリバリーと継続的デプロイの両方を指すことがあります。どちらを指しているかは、チームや文脈で確認します。

## 変更が利用者に届くまで

```text
コードを変更
  ↓
GitHubなどへpush／Pull Requestを作成
  ↓
自動チェック（書式・静的解析・テスト）
  ├─ 失敗 → 結果を確認して修正
  └─ 成功 → ビルドして配布できる形にする
                  ↓
          承認して公開（デリバリー）
          または自動で公開（デプロイ）
```

この一連の自動処理を**パイプライン**と呼びます。各作業は**ジョブ**や**ステップ**として定義されます。

## 身近なたとえ

CI/CDは、料理店の注文から提供までの流れに似ています。

- **CI**：注文内容を確認し、材料や調理手順に問題がないかチェックする
- **ビルド**：料理を提供できる形に仕上げる
- **デリバリー**：店員が最終確認してお客さんに渡す
- **デプロイ**：確認条件を満たした料理を自動で提供する

自動化しても、チェック内容が間違っていたり、手順が分かりにくかったりすれば安心できません。自動化する作業と、失敗時の直し方をチームで把握しておくことが大切です。

## CI/CDを使う理由

- **問題を早く見つける**：変更をまとめてからではなく、小さな変更ごとに確認できる
- **確認漏れを減らす**：毎回同じチェックを同じ順番で実行できる
- **リリースを繰り返しやすくする**：手作業の手順や人による違いを減らせる
- **変更の影響を小さくする**：小さく頻繁に出せば、問題の原因を追いやすい

CI/CDそのものが品質を保証するわけではありません。テストやチェックが不十分なら、問題を含んだ変更も自動で先へ進んでしまいます。

## よくあるパイプライン

Pull Requestを作ったときに、次のような確認を行います。

1. ソースコードを取得する
2. 必要な言語やツールを準備する
3. 依存ライブラリをインストールする
4. 書式・静的解析を確認する
5. 自動テストを実行する
6. アプリや配布用ファイルをビルドする
7. 必要に応じて脆弱性チェックを行う
8. 条件を満たしたら、テスト環境や本番環境へ配布する

最初から全部を自動化する必要はありません。まずはPull Requestごとに、書式確認・テスト・ビルドを自動で実行するところから始められます。

## GitHub Actionsの例

GitHub Actionsでは、YAML形式のワークフローファイルに実行条件と作業手順を書きます。次は、Node.jsプロジェクトでPull Requestとpushのたびにテストする簡単な例です。

```yaml
name: CI

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
```

この例では、コードがpushされるかPull Requestが作られると、GitHubが実行環境を用意し、依存関係をインストールしてテストします。テストが失敗した場合は、その実行結果を見て修正します。

## 安全に運用するための基本

- **秘密情報をコードに書かない**：APIキーや署名鍵は、CIサービスのSecretsなどに登録する
- **権限を必要最小限にする**：ワークフローへ不要な書き込み権限を与えない
- **本番公開の手順を決める**：承認が必要か、自動公開するかを明確にする
- **失敗ログを読めるようにする**：どのチェックで失敗したか、担当者が追える状態にする
- **失敗をむやみに再試行しない**：原因が残ったまま再実行を繰り返さず、まずログを確認する
- **公開後も確認する**：エラーや利用状況を監視し、必要なら以前の版へ戻せるようにする

認証情報や本番環境に触れるワークフローの変更は、通常のアプリコード変更より影響が大きいため、内容と権限を慎重に確認します。

## 用語の早見表

| 用語 | 意味 |
|---|---|
| ワークフロー | 自動処理全体の定義 |
| トリガー | pushやPull Requestなど、処理を開始するきっかけ |
| ジョブ | ひとまとまりの作業。テストやビルドなど |
| ステップ | ジョブの中で順に実行する個別の操作 |
| 成果物（artifact） | ビルドで作られ、保存・配布されるファイル |
| 環境 | 開発・テスト・本番など、アプリを動かす場所 |
